## Поиск: отделить тему от предпочтения продукта

В `retrieval.py` тема ценовой категории получает тот же повышающий коэффициент,
что явно выбранный продукт. В одном официальном демо-сценарии все восемь результатов
относятся к одному документу; диагностический раздел сравнения счёта остаётся
на позиции 12. Проверена абляция: оставить расширение запроса, убрать только
продуктовый приоритет категории. Нужная диагностика поднимается на позицию 4,
таблица категорий остаётся первой. Из 18 демо-запросов порядок результатов меняется
только у этого сценария.

Предложение: проверить эту узкую правку отдельно, без привязки к ID или тексту
официального примера. Результат получен на BM25 офлайн; влияние на hybrid/Qwen
и конкурсный балл пока не измерено. Удалять историю или ограничивать каждый
документ одинаковым числом фрагментов без отдельной проверки не предлагается.

## Запуск: сохранить время для генерации

`retrieval.py:211,228` использует его для query embedding и reranker. При медленном
необязательном этапе возврат к BM25 может произойти уже после исчерпания бюджета.

по таймауту, но и то, что после fallback действительно состоялась генерация.

## Ответ провайдера: отличать завершение от обрыва

`model_client.py:215–223` принимает текст без проверки `finish_reason`.
Синтетический ответ с `finish_reason=length` возвращает незавершённую фразу как
успешную. Если прокси отвергает параметр отключения рассуждений, а повтор содержит
только незакрытый блок reasoning, возникает ошибка пустого ответа даже при
оставшемся времени. Предложение: учитывать причину завершения и допускать один
ограниченный по времени повтор для диагностированного обрыва; не повышать
глобальный лимит токенов без измерений.

Эти воспроизведения подтверждают механизмы отказа. Без логов конкурсных ответов
они не доказывают причину текущего public-score 0.4877.
