# Архитектура ИИ-консультанта МТС EnergyTool

Документ задаёт границы модулей. Изменение границ — через правку этого файла.

## 1. Ограничения, из которых выведена архитектура

| Источник | Ограничение | Следствие |
|---|---|---|
| Регламент §4 | На платформу переносятся только корневые `.py` и `requirements.txt`; данные, индексы, конфиги в ZIP запрещены | Все модули ядра — плоско в корне; промпты — Python-константы; индекс строится при запуске |
| Регламент §5 | 20 минут на весь прогон, 8 CPU, 16 ГБ, без GPU | Бюджет вызовов на вопрос, параллелизм, глобальный дедлайн, деградация вместо падения |
| Регламент §6 | Один OpenAI-совместимый прокси: `/chat/completions`, `/embeddings`, `/rerank`; модели — из env | Единый HTTP-клиент; никаких hardcoded-имён и ключей |
| Регламент §6 | Разрешённые зависимости — только из списка организаторов | `httpx`, `numpy`, `bm25s`/свой BM25; без `torch`, без локальных моделей |
| Кейс, ограничения 2–5 | Факты только из базы; нет ответа → сказать и предложить специалиста; только тематика EnergyTool; ≤150 слов | Жёсткий промпт + порог достаточности контекста + пост-проверка |
| Кейс, задача 5 | Тест-кейс — одиночный вопрос или текстовая история диалога; состояние между ID не переносится | Ядро работает со списком сообщений, без глобального состояния |
| Эталоны `demo_output.csv` | Прямой ответ → факты из базы → один уточняющий вопрос; без навязывания контактов | Формат ответа закреплён в промпте |

База знаний: 19 Markdown-файлов, ~122 тыс. символов (~40 тыс. токенов), 235 фрагментов
при текущем разбиении. Целиком в контекст не помещается разумно, но эмбеддинги
всей базы считаются за один-два батч-запроса.

## 2. Общая схема

```
            ┌──────────────── batch (этап 1) ────────────────┐
questions.csv → solution.py ─┐                                │
                             ├─► consultant.answer(messages) ─► Answer(text, sources, timings, route)
web chat (этап 2) → app.py ──┘          │
                                        ├─ dialogue.py   разбор истории, запрос для поиска
                                        ├─ retrieval.py  BM25 + bge-m3 → RRF → reranker → контекст
                                        ├─ prompts.py    системный промпт и шаблоны
                                        └─ llm.py        HTTP к прокси: retry, дедлайн, очистка <think>
web-only: leads.py (сбор контактов + резюме), storage.py (SQLite: сессии, сообщения, заявки)
```

Ядро (`consultant` и всё ниже) не знает, откуда пришёл вопрос. Batch и веб — тонкие
обёртки. Это даёт одинаковое качество ответов в сабмите и в демо.

## 3. Модули (все в корне репозитория)

| Модуль | Ответственность | Входит в ZIP |
|---|---|---|
| `config.py` | Чтение env с альтернативными именами (`LLM_BASE_URL`/`OPENAI_BASE_URL`, `LLM_MODEL`/`GEN_MODEL`/`OPENAI_MODEL`, …), числовые лимиты с clamp, дефолты | да |
| `llm.py` | `chat()`, `embed()`, `rerank()`; ограниченные повторы на 429/5xx/таймаут с паузой; проверка дедлайна; удаление `<think>…</think>`; отключение режима рассуждений Qwen3 с откатом, если прокси не принимает параметр; ключи не логируются | да |
| `retrieval.py` | Загрузка ZIP, разбиение по заголовкам, BM25 (есть), плотный поиск bge-m3, слияние RRF, реранкер, сборка контекста с лимитом символов | да |
| `dialogue.py` | Разбор `Пользователь:/Ассистент:` в список сообщений; запрос для поиска из реплик пользователя; признаки (отказ давать телефон, просьба о звонке, вопрос о цене) | да |
| `prompts.py` | Системный промпт консультанта, правила формата, шаблоны отказа и уточнения | да |
| `consultant.py` | Оркестратор одного хода: маршрут → поиск → проверка достаточности → генерация → пост-обработка. Возвращает `Answer` | да |
| `solution.py` | Точка входа платформы: чтение CSV, построение индекса, пул потоков, глобальный дедлайн, гарантированная запись `submission.csv` | да |
| `leads.py` | Состояние сбора заявки (ФИО, телефон, компания), валидация, генерация резюме для менеджера | нет (этап 2) |
| `storage.py` | SQLite: сессии, сообщения, заявки, отладочные данные | нет (этап 2) |
| `app.py` + `web/` | FastAPI, чат, «Новый диалог», режим отладки, просмотр истории и заявок | нет (этап 2) |
| `eval.py` | Локальная оценка на демо-вопросах: попарное сравнение с эталоном LLM-судьёй, отчёт | нет (dev) |

Правило зависимостей: стрелки только вниз — `solution/app → consultant → {dialogue, retrieval, prompts} → llm → config`.
`leads`/`storage` зависят от `consultant`, но не наоборот.

## 4. Контракт ядра

```python
@dataclass
class Message:
    role: Literal['user', 'assistant']
    content: str

@dataclass
class Answer:
    text: str                      # готовый ответ пользователю
    route: str                     # 'answer' | 'clarify' | 'out_of_scope' | 'no_info' | 'fallback'
    sources: list[SourceRef]       # файл, заголовок, оценка — для режима отладки
    timings: dict[str, float]      # retrieval / rerank / llm / total, секунды
    offer_contact: bool            # уместно ли предложить связаться с менеджером

def answer(messages: list[Message], index: KnowledgeIndex, deadline: float | None = None) -> Answer
```

Веб-команда опирается только на этот контракт и на `leads.summarize(messages) -> LeadSummary`.

## 5. Конвейер одного хода

1. **Разбор диалога.** Последняя реплика пользователя — то, на что отвечаем. Поисковый
   запрос — последние реплики пользователя (утверждения ассистента не являются фактами).
2. **Маршрутизация без LLM.** Дешёвые правила: пустой ввод, приветствие, явная просьба о
   звонке. Тематика вне EnergyTool определяется по совокупности: слабый поиск + решение модели
   в основном вызове (отдельный вызов-классификатор не делаем, пока замеры не покажут пользу).
3. **Гибридный поиск.** BM25 top-20 и bge-m3 top-20 → Reciprocal Rank Fusion → реранкер
   top-N (≈6–8). При недоступности эмбеддингов или реранкера — откат на BM25, ответ не теряется.
4. **Сборка контекста.** Фрагменты группируются по файлу с заголовками-путями. Если в выдаче
   есть продуктовый файл, добавляются его разделы «Факты, которые можно утверждать» и
   «Чего утверждать нельзя» — это защита от выдуманных цен, сроков и имён. Лимит контекста —
   по символам, настраивается.
5. **Проверка достаточности.** Если лучший балл реранкера ниже порога — модель получает
   указание задать уточняющий вопрос или честно сказать, что в базе ответа нет, и предложить
   специалиста. Порог калибруется на демо-наборе.
6. **Генерация.** Один вызов `/chat/completions`, `temperature` из env. Формат как в эталонах:
   прямой ответ → 1–3 факта из базы применительно к ситуации клиента → один уточняющий
   вопрос, ≤150 слов, без Markdown-разметки, без названий файлов.
7. **Пост-обработка.** Удалить `<think>`, служебные метки, ссылки на «фрагменты»; обрезать
   до 10 000 символов; пустой ответ → безопасный шаблон, а не пустая строка.

Бюджет на вопрос: 1 эмбеддинг запроса, 1 реранк, 1 генерация. Переписывание запроса
отдельным вызовом LLM — только если замеры покажут прирост и бюджет времени позволит.

## 6. Batch-режим (`solution.py`)

- Индекс строится один раз: эмбеддинги всех фрагментов батчами, кэш в `/tmp` по хэшу архива.
- Вопросы обрабатываются пулом из `MAX_WORKERS` потоков.
- Глобальный дедлайн ~17 минут от старта: после него оставшиеся вопросы идут по
  облегчённому пути (BM25 + короткий вызов), а при исчерпании времени — шаблонный ответ.
- Ответы пишутся в порядке исходных ID; CSV — `csv.writer`, UTF-8, `QUOTE_ALL`.
  Промежуточная запись после каждых N ответов, чтобы тайм-аут не оставил пустой файл.
- Исключение в одном вопросе не роняет прогон.

## 7. Веб-режим (этап 2, кратко)

- Сессия хранит `list[Message]`; «Новый диалог» создаёт новую сессию, старая остаётся в SQLite.
- Сбор заявки — детерминированная логика, не LLM: когда `offer_contact` и пользователь
  согласен, бот по шагам запрашивает ФИО, телефон, компанию с валидацией. Отказ дать
  телефон уважается.
- Резюме для менеджера — отдельный вызов LLM в JSON (задача, объект, подходящие продукты,
  известные параметры, открытые вопросы) → человекочитаемый текст.
- Режим отладки показывает `Answer.sources`, `Answer.timings`, `route`.
- Передача заявок менеджеру: в прототипе — таблица заявок и экспорт; в README — схема
  интеграции через webhook в CRM (реальная отправка не требуется).

## 8. Локальная разработка и оценка

- Локально используем ту же модель, что на платформе: OpenRouter, `qwen/qwen3.8-27b`,
  эмбеддинги `baai/bge-m3` (см. `.env.example`). Qwen3 Reranker на OpenRouter нет — локально
  `RERANKER_MODEL` пуст и ядро идёт по пути без реранжирования; путь с реранкером проверяется сабмитом.
- Отключение рассуждений различается: OpenRouter — `reasoning: {"enabled": false}`, vLLM-подобный
  прокси платформы — вероятно `chat_template_kwargs: {"enable_thinking": false}`. `llm.py` передаёт
  вариант по провайдеру и в любом случае вырезает `<think>`.
- `eval.py`: прогон 18 демо-вопросов, попарное сравнение с эталоном в двух порядках
  (как у организаторов), метрики Match Rate / Win Rate, время ответа. Каждое изменение
  промпта или поиска проверяется до сабмита.
- Модульные тесты (`tests/`) проверяют контракты на синтетических данных и моках API,
  не качество модели.

## 9. Риски

| Риск | Мера |
|---|---|
| Qwen3 выводит рассуждения `<think>` и тратит токены/время | Отключение рассуждений в запросе + вырезание тегов |
| Число проверочных вопросов неизвестно, лимит 20 мин | Дедлайн, деградация, промежуточная запись CSV |
| Кейс разрешает включить готовый индекс, регламент — запрещает | Следуем регламенту: индекс строится при запуске |
| Неизвестен формат ответа `/rerank` на прокси | Разбор `results`/`data`, откат на порядок RRF |
| Локальная модель отличается от платформенной | Финальная настройка — по сабмитам; промпт без опоры на особенности других LLM |
